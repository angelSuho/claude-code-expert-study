## TDD 필수 규칙

### Red-Green-Refactor 사이클

1. **Red**: 먼저 실패하는 테스트를 작성한다
   - 테스트가 실제로 실패하는지 확인
   - 실패 이유가 예상대로인지 확인

2. **Green**: 테스트를 통과시키는 최소한의 코드 작성
   - "최소한"은 정말 최소한을 의미
   - 하드코딩도 허용 (다음 테스트가 일반화를 강제)

3. **Refactor**: 테스트가 통과하는 상태에서 코드 개선
   - 중복 제거
   - 명확한 이름 사용
   - 구조 개선

### 금지 사항

- ❌ 테스트 없이 구현 코드 작성
- ❌ 테스트와 구현을 동시에 작성
- ❌ 테스트 skip 또는 주석 처리
- ❌ expect 조건을 느슨하게 변경
- ❌ 실패 원인 분석 없이 테스트 수정

### 필수 확인

- "go"라고 하면 다음 순서로 진행:
  1. 다음 테스트 케이스 식별
  2. 실패하는 테스트 작성
  3. 테스트 실행하여 실패 확인
  4. 최소 구현
  5. 테스트 통과 확인
  6. 리팩터링 (필요 시)
  7. 전체 테스트 실행

## 대화 흐름 예시

### 나쁜 대화 흐름

**개발자**: "이메일 검증 기능 만들어줘"

**AI**: "네, EmailValidator 클래스를 만들고 테스트도 함께 작성하겠습니다."

→ [동시에 구현과 테스트 생성] ← TDD 원칙 위반

---

### 좋은 대화 흐름

**개발자**: "이메일 검증 기능을 TDD로 만들자. 먼저 유효한 이메일에 대한 실패하는 테스트만 작성해줘."

**AI**: "네, 실패하는 테스트를 먼저 작성하겠습니다."

```typescript
describe('EmailValidator', () => {
  it('유효한 이메일 주소를 검증한다', () => {
    const validator = new EmailValidator();
    expect(validator.isValid('user@example.com')).toBe(true);
  });
});
```

"EmailValidator 클래스가 없으므로 이 테스트는 실패합니다."

**개발자**: "좋아. 이제 이 테스트를 통과시키는 최소 코드를 작성해줘."

**AI**: "최소한의 구현을 작성하겠습니다."

```typescript
class EmailValidator {
  isValid(email: string): boolean {
    return true; // 최소 구현 - 다음 테스트가 일반화를 강제
  }
}
